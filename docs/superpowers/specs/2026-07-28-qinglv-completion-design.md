# 拾光手账 A→B→C 完善设计规格

日期：2026-07-28

## 1. 目标

按以下顺序把现有项目从“核心功能可用”推进到“功能闭环、可维护、可上线”：

1. **A：功能与体验闭环**：补齐后端已经提供但前端缺失的功能，统一关键交互状态，并降低页面复杂度。
2. **B：工程质量**：补齐前端质量门禁与测试，增强后端接口测试和本地开发可重复性。
3. **C：上线安全与稳定性**：移除生产默认密钥，强化上传、并发、健康检查和部署验收。

每个阶段都必须在本阶段范围内完成构建与验证后再进入下一阶段。

## 2. 当前基线

- 前端：Vue 3 + Vite，`npm run build` 当前通过。
- 后端：Spring Boot 3.2 + Java 17 + MyBatis-Plus，使用 JDK 17 时 21 项现有测试通过。
- 环境问题：本机默认 Maven 使用 JDK 11，直接执行 Maven 会因 `release 17` 失败；项目需要固定使用 JDK 17。
- 前端当前没有 ESLint、Prettier、Vitest 或组件测试配置。
- `AnniversaryView.vue` 只接入了创建接口，后端已有更新/删除接口未形成前端闭环。
- `WishListView.vue` 只接入创建/完成/删除，已有更新 API 未提供编辑入口。
- 多个页面使用原生 `confirm` 和重复的错误/加载处理；大型页面文件集中在 500～1000 行。
- 部署脚本和 Compose 配置仍存在可直接运行的默认密码/密钥。

## 3. 设计原则

### 3.1 方案选择

考虑过三种路线：

- **渐进式增强（采用）**：沿用现有 Vue/Spring 分层，新增小型共享组件/组合式函数，按模块增量改造。风险最低，能保留现有视觉风格。
- 引入完整 UI 组件库：可以快速统一交互，但会改变当前手账风格并增加依赖、包体积和迁移成本。
- 大范围重构前端：长期边界更清晰，但会延迟功能价值，且难以在没有产品验收环境的情况下控制回归。

采用渐进式增强，明确不做与目标无关的框架迁移或全量重写。

### 3.2 兼容原则

- 不改变已公开 API 的路径和主要响应结构。
- 前端继续通过 `/api` 访问后端。
- 数据库迁移只新增必要约束/字段或索引，不破坏现有数据。
- 对已经存在的旧字段兼容读取，例如纪念日 `name/title`、`startDate/togetherDate`。
- 敏感信息不写入日志、不返回前端、不硬编码到部署脚本。

## 4. 阶段 A：功能与体验闭环

### 4.1 纪念日管理闭环

- 增加编辑入口，复用新增表单并带入当前数据。
- 增加删除入口，使用统一确认交互。
- 支持标题、日期、类型、图标、备注及每年重复设置。
- 保存期间禁止重复提交；失败时保留输入。
- 新增、编辑、删除后保持当前页面状态。

### 4.2 心愿编辑闭环

- 支持修改标题、描述、图标、分类和优先级。
- 编辑动作不意外重置完成状态。
- 新增与编辑复用一套表单状态和校验逻辑。

### 4.3 统一前端交互基础设施

新增轻量共享能力，不引入大型 UI 库：

- `BaseModal`：统一弹层、ESC 关闭、遮罩行为、移动端宽度和焦点体验。
- `ConfirmDialog`：统一危险操作确认和确认中状态。
- `EmptyState`、`LoadingState`、`ErrorState`：统一列表反馈。
- 轻量异步组合式函数：统一 loading、错误捕获和重复提交保护。
- 保留现有手账视觉变量与动画。

### 4.4 页面体验改进

重点覆盖首页、纪念日、心愿、相册、惊喜和小窝：

- 初次加载、刷新、空列表、接口失败均有明确反馈。
- 删除成功后优先就地更新，避免不必要的全量刷新。
- 表单增加长度、必填和日期校验。
- 原生 `confirm` 全部替换为统一确认弹窗。
- 移动端弹窗不溢出视口，关键按钮具有足够触控区域。
- 网络失败时尽量保留用户输入。

### 4.5 阶段 A 验收标准

- 纪念日可新增、编辑、删除；心愿可新增、编辑、完成、删除。
- 现有笔记、相册、惊喜、空间功能没有回归。
- 前端生产构建成功。
- 关键页面在桌面和窄屏下均可正常操作。

## 5. 阶段 B：工程质量

### 5.1 前端质量门禁

- 增加 ESLint + Vue 规则。
- 增加 Prettier 配置。
- 增加 Vitest 与 Vue Test Utils。
- 增加 `lint`、`lint:fix`、`format:check`、`test`、`test:watch`、`check` 脚本。
- 新增和修改文件达到零 lint 错误，并逐步修复历史机械性问题。

### 5.2 测试范围

前端优先覆盖：

- user/couple/theme store 的关键状态和持久化。
- API 请求拦截器的成功、业务错误、401 和超时处理。
- 纪念日、心愿及共享确认组件的关键交互。

后端增加：

- Controller 参数校验和统一错误响应测试。
- 纪念日、心愿、上传接口的权限与参数边界测试。
- 点赞重复和并发场景测试。
- 保留现有测试并确保全部通过。

### 5.3 本地开发可重复性

- 增加 Windows Git Bash 环境检查脚本，明确要求 JDK 17、Node 和 Maven。
- README 增加环境检查、测试顺序和 JDK 11 常见问题说明。
- 前端检查和后端单测可独立运行。

### 5.4 阶段 B 验收标准

- `npm run check` 通过。
- `npm test -- --run` 通过。
- 使用 JDK 17 执行 `mvn test` 通过。
- README 与实际命令一致。

## 6. 阶段 C：上线安全与稳定性

### 6.1 密钥与配置安全

- Compose 不再提供可用于生产的固定默认密码或 JWT 密钥。
- 部署前检查 `.env`、占位符、JWT 密钥长度和 CORS 来源，不满足则 fail fast。
- 部署脚本不输出完整密钥。
- 文档、示例配置和日志中不保留真实部署地址或敏感值。

### 6.2 文件上传

- 保持扩展名 + MIME 校验，并增加文件名、路径规范化和异常回滚。
- 数据库写入失败时删除已落盘文件，避免孤儿文件。
- 禁止路径穿越。
- 为上传大小和类型边界增加测试。

### 6.3 点赞一致性

- 使用数据库原子更新或可靠的唯一键切换策略，避免并发覆盖计数。
- 重复请求返回稳定结果，计数不为负数。
- 增加重复和并发调用测试。

### 6.4 运行与部署

- 增加后端健康检查。
- Compose healthcheck 覆盖 MySQL、后端和前端。
- 部署脚本使用条件等待，不把固定 `sleep` 作为唯一判断。
- 增加备份、恢复和已有数据库迁移说明。
- 校验 nginx API、上传及 SPA fallback 路由。

### 6.5 阶段 C 验收标准

- 缺少安全配置时生产部署明确失败。
- 上传异常不留下可确认的孤儿文件，路径穿越被拒绝。
- 点赞重复和并发测试通过。
- Docker 可用时，Compose 配置、镜像构建和健康检查通过。
- API 验收脚本覆盖核心双人流程与权限拒绝。

## 7. 交付顺序

1. 完成阶段 A，运行前端构建与关键交互检查。
2. 完成阶段 B，把检查命令纳入项目文档。
3. 完成阶段 C，运行全量验证和 API 验收。
4. 最终交付变更清单、运行命令、验证结果和环境限制。

## 8. 明确不做

- 不更换 Vue、Spring Boot 或数据库技术栈。
- 不引入重量级 UI 组件库。
- 不改造成多人社区、聊天系统或对象存储架构。
- 不在没有迁移必要性的情况下重写数据库模型。
